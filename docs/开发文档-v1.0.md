## 1. 文档说明

本文档是 EAER 首期 16 周开发与验收的唯一依据。它合并了《技术方案修订稿 v1.1》《技术详细设计 v0.1》和评测数据集调研的全部决定，并为每个部分规定验收方式；与前序文档冲突时以本文为准。

**读者。** 研发、测试、产品、交付。

**首期范围。** 核心引擎、三个对接接口及其参考实现、评测工具、精简版与集群版两种部署形态。

**不在首期范围。** 前端界面、客户现场的数据源连接器与 SSO 对接、客户自部署模型的调优。

### 1.1 术语

| 术语 | 含义 |
| --- | --- |
| 文档 | 一份逻辑文档，例如一份制度。一份文档有多个版本 |
| 版本 | 文档的一次具体内容，审核、发布、归档都以版本为对象 |
| 证据 | 可被引用和验证的最小单元：一个段落、一个表格单元格或一个图表 |
| 规范类 / 记录类 | 规范类（制度、规范、合同、标准）维护生效区间；记录类（报告、纪要、设计文档）只有文档日期 |
| 有效期 | 版本实际生效的区间，即 `valid_from` 到 `valid_to` |
| 系统时间 | 系统获知某个版本的时间，取审核通过时间 `approved_at` |
| 来源等级 | 时间值的可信程度：`explicit`、`inferred`、`unknown` |
| 授权范围 | 用户可访问的租户与角色集合，由授权接口解析得出 |
| 回溯查询 | 按系统时间回答“截至某天系统知道什么” |
| 强制验证清单 | 必须走 Verified 模式的规则集合，客户只能增加，不能缩小 |

### 1.2 验收总则

每个部分末尾都有验收表，验收项编号为 `AC-章节-序号`。

| 验收方式 | 说明 | 执行时机 |
| --- | --- | --- |
| 自动化测试 | 单元、集成、端到端测试 | 每次合并代码时在 CI 中运行 |
| 评测 | `eval` 模块在评测集上计算指标 | 每个阶段关口，及模型或索引变更后 |
| 人工检查 | 评审、抽检、演练 | 阶段关口 |
| 安全测试 | 自动化越权用例加人工红队 | 自动化部分随 CI，红队在第 13–16 周 |

两类验收项：

- **硬性项。** 有一条不通过就不能发布，不接受豁免。这类项目由确定性代码保证，与所用模型无关。
- **指标项。** 门槛标注“待基线”的，在对应阶段的基线评测后由产品和研发共同确定，回填到本文第 16 节。未达门槛需要书面豁免才能进入下一阶段。

文中标注“初值”的参数，在评测后校准。

## 2. 系统概述

EAER 是面向多家客户交付的标准 RAG 产品：用户不仅得到答案，还能看到答案来自哪份文档的哪个版本、哪一页或哪个图表，以及该证据在目标时间是否有效。

| 核心能力 | 说明 |
| --- | --- |
| 三种执行模式 | Fast 快速检索，Deep 多步推理，Verified 增强验证；由 Router 选择，可逐级升级 |
| 验证层 | 代码做确定性检查，模型做语义检查；拿不准的标为“未验证” |
| 时间处理 | 版本级有效期，每个时间值带来源等级；支持当前、历史时点、回溯三类时间查询 |
| 文档生命周期 | 审核通过才可搜索；可搜索后只能归档；归档可以撤销 |
| 权限 | 授权范围下推到索引，证据返回前在数据库中再核对一次 |
| 多模态 | 文本、表格、图表统一为证据；图表在入库时解析成结构化内容 |

两种部署形态共用一套代码：

| 形态 | 适用客户 | 模型 |
| --- | --- | --- |
| 精简版 | 人少、并发低、文档量可能极大 | 调用线上模型接口 |
| 集群版 | 并发高、多部门使用 | 线上模型，或客户自部署模型 |

## 3. 总体架构

首期是模块化单体：一个代码库、8 个模块、2 个进程。模块之间只通过接口调用；集群版按模块拆分部署，代码不变。

### 3.1 模块

| 模块 | 职责 | 运行位置 |
| --- | --- | --- |
| `query-api` | 对外接口、会话、流式输出、身份校验 | 接口进程 |
| `orchestrator` | Router、三种模式的状态机、预算控制 | 接口进程 |
| `retrieval` | 混合检索与重排；下推权限、时间过滤；检索后数据库核对 | 接口进程 |
| `verifier` | 结论拆分、确定性检查、语义检查 | 接口进程 |
| `lifecycle` | 审核、发布、归档、取消归档、版本链与有效区间 | 接口进程 |
| `ingestion` | 解析、分类、时间与关系抽取、建索引 | 后台任务进程 |
| `adapters` | 数据源、授权、模型三个对接接口及参考实现 | 两个进程共用 |
| `eval` | 评测集生成与校验、跑评测、标定阈值、准入检查、能力矩阵 | 离线运行，同时作为客户自助评测工具 |

### 3.2 边界规则

1. 只有 `retrieval` 读检索索引；只有 `ingestion` 和 `lifecycle` 写检索索引。
2. 只有 `lifecycle` 能改变版本状态。
3. 所有模型调用都经 `adapters` 的模型接口，业务模块不直接依赖任何模型厂商的 SDK。
4. 授权范围只以句柄形式在模块间传递，不进入模型上下文。

### 3.3 技术栈

版本于 2026 年 11 月 11 日按 PyPI 与 GitHub 的发布记录锁定，规则如下：

- **选发布满 14 天的最新稳定版。** 刚发布的版本可能带有未被发现的缺陷或恶意代码，因此跳过 2026 年 10 月 28 日之后发布的版本。
- **Python 用 3.14。** 3.15 刚发布不久，Docling 等依赖的适配需要时间，首期不采用。
- **PostgreSQL 用 18。** 19 仍是候选版；18.7 已打标签但未满 14 天，正式发布后作为安全更新升级。
- **依赖清单固定到精确版本并附哈希。** 每月评估一次升级；安全补丁随时升级，升级后重跑全部硬性项。
- **中文分词。** 已按 AC-5-4 选定 OpenSearch 内置的 standard 分词器（中文按字切分，2026-11-13）：在合成集 v2 测试集（1400 条）上，问法与原文用词相同时五种候选召回都在 92% 左右；问法改写、不含原文用词时 standard 最高（仅关键词 86.7%，关键词加向量 91.2%），smartcn、icu、jieba 依次落后（加向量后 85.4%–87.3%）。smartcn、icu 插件与应用侧 jieba 保留为可选（环境变量 EAER\_TEXT\_ANALYZER），换分词器需重建索引；结论来自合成数据，接入真实语料后复核。

## 4. 数据模型

PostgreSQL 保存全部事实和历史，共 12 张核心表（第 12 张为开发中新增的向量缓存 evidence\_embedding，见 5.3）；检索索引只是它的派生物，可以随时重建。有效期和关系两张表一旦记录就只追加，回溯查询靠它们复现当时的认知。

### 4.1 表清单

| 表 | 作用 |
| --- | --- |
| `tenant_config` | 租户配置：强制验证清单、阈值、语言与分词器、预算 |
| `acl_policy` | 访问策略：可访问的角色和用户组 |
| `document` | 逻辑文档 |
| `document_version` | 文档版本：状态、系统时间、权限 |
| `version_validity` | 版本有效期及来源等级，含更正历史 |
| `version_relation` | 版本之间的取代、冲突、引用关系 |
| `evidence` | 证据单元 |
| `lifecycle_event` | 发布、归档、取消归档、权限变更、有效期更正的事件记录 |
| `review_task` | 审核任务 |
| `ingest_job` | 入库与索引任务，同时充当精简版的任务队列 |
| `query_log` | 每次提问的完整记录 |

### 4.2 表结构

```sql
CREATE TABLE tenant_config (
  tenant_id           text PRIMARY KEY,
  forced_verify_rules jsonb NOT NULL DEFAULT '[]',
  thresholds          jsonb NOT NULL DEFAULT '{}',   -- 路由、验证、准入阈值
  budgets             jsonb NOT NULL DEFAULT '{}',   -- 各模式检索轮数与时限
  language_config     jsonb NOT NULL DEFAULT '{}',   -- 分词器、Embedding 模型
  trace_retention_days int  NOT NULL DEFAULT 30,
  updated_at          timestamptz NOT NULL
);

CREATE TABLE acl_policy (
  id          uuid PRIMARY KEY,
  tenant_id   text NOT NULL,
  principals  text[] NOT NULL,          -- 角色或用户组标识
  source      text NOT NULL CHECK (source IN ('reference', 'connector')),
  updated_at  timestamptz NOT NULL
);

CREATE TABLE document (
  id          uuid PRIMARY KEY,
  tenant_id   text NOT NULL,
  source_ref  text NOT NULL,            -- 数据源中的标识
  title       text NOT NULL,
  doc_type    text CHECK (doc_type IN ('normative', 'record')),  -- 审核确认前可为空
  language    text,
  created_at  timestamptz NOT NULL,
  UNIQUE (tenant_id, source_ref)
);

CREATE TABLE document_version (
  id                uuid PRIMARY KEY,
  document_id       uuid NOT NULL REFERENCES document(id),
  version_no        int  NOT NULL,
  status            text NOT NULL
    CHECK (status IN ('pending_review', 'searchable', 'archived')),
  content_hash      text NOT NULL,
  raw_object_uri    text NOT NULL,
  acl_policy_id     uuid NOT NULL REFERENCES acl_policy(id),
  uploaded_at       timestamptz NOT NULL,
  source_created_at timestamptz,
  import_batch_id   uuid,
  approved_at       timestamptz,        -- 系统时间起点，只写一次
  archived_at       timestamptz,        -- 当前是否归档；历史见 lifecycle_event
  doc_date          date,               -- 记录类文档的时点
  parser_version    text NOT NULL,
  UNIQUE (document_id, version_no)
);

CREATE TABLE version_validity (
  id               uuid PRIMARY KEY,
  version_id       uuid NOT NULL REFERENCES document_version(id),
  valid_from       date,
  valid_from_grade text NOT NULL CHECK (valid_from_grade IN ('explicit', 'inferred', 'unknown')),
  valid_to         date,
  valid_to_grade   text NOT NULL CHECK (valid_to_grade IN ('explicit', 'inferred', 'unknown')),
  valid_to_reason  text CHECK (valid_to_reason IN ('new_version', 'superseded', 'stated')),
  unresolved_text  text,                -- 无法解析的相对表述原文
  locator          jsonb,               -- 原句位置，或补录人
  recorded_at      timestamptz,         -- 发布时写入；为空表示审核前的待确认值
  replaced_at      timestamptz          -- 被更正的时间；为空表示当前值
);

CREATE TABLE version_relation (
  id              uuid PRIMARY KEY,
  relation        text NOT NULL CHECK (relation IN ('supersedes', 'conflicts', 'references')),
  from_version_id uuid NOT NULL REFERENCES document_version(id),
  to_version_id   uuid NOT NULL REFERENCES document_version(id),
  grade           text NOT NULL CHECK (grade IN ('explicit', 'inferred')),
  locator         jsonb,
  recorded_at     timestamptz,          -- 同 version_validity
  retracted_at    timestamptz
);

CREATE TABLE evidence (
  id            text PRIMARY KEY,       -- 规则见 4.3
  version_id    uuid NOT NULL REFERENCES document_version(id),
  modality      text NOT NULL CHECK (modality IN ('text', 'table', 'figure')),
  locator       jsonb NOT NULL,         -- page、section、table_id、row、column、bbox
  content       text NOT NULL,          -- 表格与图表为解析后的结构化文本
  content_hash  text NOT NULL,
  parse_stage   text NOT NULL CHECK (parse_stage IN ('text', 'deep')),
  created_at    timestamptz NOT NULL
);

CREATE TABLE lifecycle_event (
  id          uuid PRIMARY KEY,
  version_id  uuid NOT NULL REFERENCES document_version(id),
  event       text NOT NULL CHECK (event IN
    ('published', 'archived', 'unarchived', 'acl_changed', 'validity_corrected')),
  actor       text NOT NULL,
  detail      jsonb,
  occurred_at timestamptz NOT NULL
);

CREATE TABLE review_task (
  id          uuid PRIMARY KEY,
  tenant_id   text NOT NULL,            -- 删除待审核版本后任务不再指向版本，仍按租户列出
  version_id  uuid REFERENCES document_version(id),  -- 删除后为空：只保留删除人与时间（6.5）
  batch_id    uuid,
  status      text NOT NULL CHECK (status IN ('open', 'approved', 'deleted')),
  corrections jsonb,
  reviewer    text,
  decided_at  timestamptz
);

CREATE TABLE ingest_job (
  id           uuid PRIMARY KEY,
  version_id   uuid REFERENCES document_version(id),
  stage        text NOT NULL CHECK (stage IN ('receive', 'parse_text', 'classify_extract',
                 'publish_index', 'parse_deep', 'index_update', 'reindex')),
  status       text NOT NULL CHECK (status IN ('queued', 'running', 'done', 'failed')),
  priority     int  NOT NULL DEFAULT 100,
  attempts     int  NOT NULL DEFAULT 0,
  last_error   text,
  locked_until timestamptz,
  created_at   timestamptz NOT NULL,
  updated_at   timestamptz NOT NULL
);

CREATE TABLE query_log (
  id             uuid PRIMARY KEY,
  tenant_id      text NOT NULL,
  session_id     uuid NOT NULL,
  user_id        text NOT NULL,
  asked_at       timestamptz NOT NULL,
  question       text NOT NULL,
  time_basis     jsonb,                 -- as_of_valid、as_of_system 及其来源（解析或参数）
  mode           text NOT NULL,
  mode_path      text[] NOT NULL,       -- 例如 {fast,deep,verified}
  status         text NOT NULL CHECK (status IN ('running', 'completed', 'cancelled', 'failed')),
  answer         text,
  claims         jsonb NOT NULL DEFAULT '[]',
  evidence_ids   text[] NOT NULL DEFAULT '{}',
  abstained      boolean NOT NULL DEFAULT false,
  authz_decision jsonb NOT NULL,
  model_id       text NOT NULL,
  index_build_id text NOT NULL,
  cost           jsonb                  -- token、模型调用次数、各阶段耗时
);
```

### 4.3 证据 id 规则

证据 id 由内容决定：`ev_` 加上 SHA-256 的前 16 位十六进制，哈希输入为版本 id、模态、规范化后的定位和内容哈希。同一版本重新解析时，内容不变的证据得到相同的 id，历史引用不会失效。

### 4.4 不变量

| 不变量 | 保证方式 |
| --- | --- |
| 只有待审核的版本可以删除；删除时原件、证据、待确认值、入库任务一并清除，审核任务只保留删除人和时间 | 触发器拒绝删除非待审核版本；删除由 `lifecycle` 在一个事务内完成 |
| `approved_at` 只写一次 | 触发器拒绝修改已有值 |
| `recorded_at` 已写入的有效期行和关系行不可修改，只能写入 `replaced_at` 或 `retracted_at` | 触发器 |
| 每个版本同一时刻只有一行当前有效期 | 部分唯一索引：`version_id`，条件为 `recorded_at` 非空且 `replaced_at` 为空 |
| 已归档版本不在索引中 | 归档事务内排入索引删除任务；对账脚本每小时检查 |
| 证据 id 保持稳定 | 4.3 的生成规则 |
| `query_log` 保留回答、结论、所引证据、授权决定和模型标识 | 写入时校验必填字段 |

`recorded_at` 为空的行是审核前的待确认值，审核人可以直接修改；发布时统一写入 `approved_at`，此后不可修改。

### 4.5 验收

| 编号 | 验收内容 | 方式 | 通过标准 |
| --- | --- | --- | --- |
| AC-4-1 | 迁移脚本在空库执行成功，回滚脚本可恢复上一版本 | 自动化 | 全部通过 |
| AC-4-2 | 对 4.4 的每条不变量构造违规操作：删除可搜索版本、改写 `approved_at`、修改已记录的有效期行、同一版本写入两行当前有效期 | 自动化 | 每个违规操作均被数据库拒绝（硬性） |
| AC-4-3 | 证据 id 稳定：同一文件解析两次，id 集合一致；修改其中一段后，只有该段 id 变化 | 自动化 | 全部通过 |
| AC-4-4 | 删除彻底：删除待审核文档后，数据库、文件存储、索引中均无残留 | 自动化 | 残留为 0（硬性） |
| AC-4-5 | 回溯可复现：按事实表样例回放事件，对任意时刻 T 重复回放两次，结果一致 | 自动化 | 全部一致（硬性） |

## 5. 检索索引

索引中每条记录是一个证据单元，只收录可搜索状态的版本；权限和时间字段冗余进索引，过滤在引擎内完成。

### 5.1 字段与映射

| 字段 | 类型 | 用途 |
| --- | --- | --- |
| `evidence_id`、`version_id`、`document_id` | keyword | 回查数据库 |
| `tenant_id` | keyword | 租户隔离，每次查询必带 |
| `principals` | keyword 数组 | 权限过滤 |
| `doc_type` | keyword | 强制验证判断 |
| `modality` | keyword | 文本、表格、图表 |
| `text` | text，分词器按租户配置 | 关键词检索 |
| `embedding` | knn\_vector，维度随 Embedding 模型 | 向量检索 |
| `approved_at` | date | 回溯过滤 |
| `valid_from`、`valid_to` | date | 生效时间过滤，存当前值 |
| `valid_grade` | keyword | 排序和来源说明 |
| `doc_date` | date | 记录类文档的时点 |
| `index_build_id` | keyword | 重建切换与缓存键 |

### 5.2 检索流程

1. `retrieval` 入口检查授权范围，缺失则抛出异常。
2. 把授权范围编译成 `tenant_id` 和 `principals` 两个过滤条件，与时间过滤一起放入查询的 filter 部分。
3. 关键词检索与向量检索各取前 50 条（初值），用 RRF 融合，k 取 60。
4. 融合后的前 50 条先做第 5 步的数据库核对，再经模型接口重排，取前 10 条（初值）；先核对可以避免为会被剔除的候选付重排费用。
5. 在数据库中核对这些证据的版本状态和权限，剔除不通过的，见第 10 节。

### 5.3 索引更新

| 事件 | 索引操作 |
| --- | --- |
| 审核通过 | 写入该版本的文本证据 |
| 深度解析完成 | 追加表格和图表证据 |
| 新版本生效，或有效期被更正 | 更新相关版本的 `valid_from`、`valid_to`、`valid_grade` |
| 权限变更 | 更新 `principals`，清除相关缓存 |
| 归档 | 按 `version_id` 删除 |
| 取消归档 | 从 `evidence` 表重新写入该版本全部证据，有效期和权限取当前值；向量取自 evidence\_embedding 缓存，不重新调用模型，只有更换 Embedding 模型时才重新计算 |
| 更换 Embedding 模型或分词器 | 新建索引全量重建，完成后切换别名，旧索引保留 24 小时后删除 |

索引更新通过 `ingest_job` 异步执行，P95 延迟目标为 60 秒（初值）。在延迟窗口内，第 5.2 节第 5 步的数据库核对保证结果正确。

### 5.4 验收

| 编号 | 验收内容 | 方式 | 通过标准 |
| --- | --- | --- | --- |
| AC-5-1 | 过滤下推：检查每个检索请求的查询结构，必含 `tenant_id` 和 `principals` 过滤；缺少授权范围的调用抛出异常 | 自动化 | 违规数为 0（硬性） |
| AC-5-2 | 索引一致性：对账脚本比较数据库中可搜索版本集合与索引中的 `version_id` 集合 | 自动化：每个事件类型触发后运行 | 延迟窗口过后差异为 0 |
| AC-5-3 | 别名切换：重建期间持续发起查询 | 自动化：集成测试 | 查询无中断；同一次查询不混用新旧索引 |
| AC-5-4 | 检索召回：Hybrid Recall@10 | 评测：中文、英文分别统计 | 均不低于 90% |
| AC-5-5 | 检索后核对：在索引中人为保留一条已归档版本的证据 | 自动化 | 返回结果不包含它（硬性） |

## 6. 入库流水线与文档生命周期

文档经 6 个阶段入库，审核是第 4 步：审核之前的产物都不进索引，审核通过后才建索引；进入搜索后只能归档，归档可以撤销。

### 6.1 支持的格式

PDF（含扫描件，走 OCR）、DOCX、PPTX、XLSX、图片、HTML。

### 6.2 六个阶段

| 阶段 | 输入 | 处理 | 输出 |
| --- | --- | --- | --- |
| 1 接收 | 原件、来源信息 | 保存原件，计算内容哈希；同一租户内哈希相同视为重复，返回已有版本；登记上传时间、源系统创建时间、导入批次 | `document`、`document_version`（待审核） |
| 2 文本解析 | 原件 | 提取正文、章节、页码和定位；切分为证据单元 | `evidence`（`parse_stage` 为 text） |
| 3 分类与抽取 | 文本证据 | 判断规范类或记录类；抽取生效与作废时间、文档日期、废止关系（规则见第 7 节） | 待确认的 `version_validity`、`version_relation`，`document.doc_type` 建议值 |
| 4 审核 | 前三步结果 | 生成 `review_task`；审核人逐份或批量通过、更正或删除 | 审核决定 |
| 5 发布 | 审核通过的版本 | 见 6.4 | 版本变为可搜索，文本证据进索引 |
| 6 深度解析 | 原件 | 后台解析表格和图表，转为结构化文本证据；不阻塞发布 | `evidence`（`parse_stage` 为 deep），追加进索引 |

每个阶段对应一条 `ingest_job`。后台进程用 `SELECT … FOR UPDATE SKIP LOCKED` 领取任务，按优先级执行，失败重试 3 次（初值），中断后从未完成的阶段续跑。解析器通过统一接口接入：Docling 是生产首选，负责 PDF、扫描件、PPTX、XLSX；Word 与 HTML 另有不依赖模型的原生解析器，用于测试，也作为这两种格式的轻量实现。

**批量导入。** 同一导入批次的版本，上传时间不作为任何时间依据，改用源系统创建时间或文件自身的修改时间。

**文档分类。** 先用规则：标题含“办法、规定、制度、规范、标准、细则、合同、协议”判为规范类，含“报告、纪要、总结、分析、方案”判为记录类；规则无法判断时由模型建议。分类结果在审核时确认。

### 6.3 审核

- 审核任务可按批次列出，审核决定可以逐份提交，也可以一次提交多份。
- 批量提交时每份单独成事务，返回每份的结果；一份失败不影响其他份。
- 审核人可以更正文档类型、有效期、来源等级和关系。补录的时间记为 `explicit`，`locator` 中记录补录人。
- 审核人可以删除待审核的版本。
- 不提供按规则自动通过。

### 6.4 发布

发布在一个数据库事务内完成：

1. 状态改为可搜索，写入 `approved_at`。
2. 该版本待确认的有效期行和关系行写入 `recorded_at`，取值等于 `approved_at`。
3. 如果是同一文档的新版本，关闭上一版本的有效区间，规则见第 7.3 节；关闭以新增有效期行的方式记录。
4. 写入 `lifecycle_event`（published）。
5. 排入索引任务：写入本版本证据，更新上一版本的有效期字段。

### 6.5 状态转换

| 当前状态 | 事件 | 下一状态 | 动作 |
| --- | --- | --- | --- |
| 无 | 上传或同步 | 待审核 | 执行第 1–3 阶段 |
| 待审核 | 审核人更正 | 待审核 | 修改待确认值，记录更正人 |
| 待审核 | 审核通过 | 可搜索 | 执行 6.4，排入第 6 阶段 |
| 待审核 | 删除 | 已删除 | 物理删除原件、证据、待确认值和入库任务；审核任务改为“已删除”，只保留删除人和时间 |
| 可搜索 | 归档 | 已归档 | 写入 `archived_at`；从索引删除；清除相关缓存；记录事件 |
| 已归档 | 取消归档 | 可搜索 | 清空 `archived_at`；重新写入索引；清除相关缓存；记录事件 |
| 可搜索 | 权限变更 | 可搜索 | 先更新数据库，再更新索引的 `principals`；清除相关缓存；记录事件 |
| 可搜索 | 有效期更正 | 可搜索 | 新增有效期行，旧行写入 `replaced_at`；更新索引；记录事件 |

除上表外的转换一律拒绝，包括删除可搜索或已归档的版本、归档待审核的版本，以及更正已归档版本的有效期（先取消归档再更正）。权限变更是文档属性的更新、不改变状态：待审核与已归档的版本同样跟随新的权限策略，只有可搜索的版本记录事件并更新索引；否则撤权会在审核通过或取消归档后丢失（AC-10-3）。

### 6.6 归档与取消归档

- 归档以文档为单位，作用于该文档当前全部可搜索的版本；取消归档恢复这些版本。
- 归档之后的提问一律查不到该文档，历史时点查询和回溯查询也不例外。归档前已开始的会话，归档后的新提问同样查不到。
- 已生成的历史回答保留引用记录；点击引用时提示“该资料已归档”，不展示原文。取消归档后恢复展示。
- 取消归档不需要重新审核，`approved_at` 保持首次发布的时间。
- 归档期间如有新版本发布，旧版本的有效区间照常关闭；恢复后按当前有效期参与检索，不会重新成为现行版本。
- 首期不提供强制删除通道。

### 6.7 验收

| 编号 | 验收内容 | 方式 | 通过标准 |
| --- | --- | --- | --- |
| AC-6-1 | 格式覆盖：每种格式 20 份样本，每份抽 5 条证据核对页码与定位 | 人工检查 | 定位正确率不低于 95%（初值） |
| AC-6-2 | 续跑：在每个阶段注入进程终止故障 | 自动化 | 恢复后全部完成，无重复证据 |
| AC-6-3 | 状态机：状态转换表每一行各一个用例，每个非法转换各一个用例 | 自动化 | 合法转换全部成功，非法转换全部拒绝（硬性） |
| AC-6-4 | 待审核不可搜：上传后、审核前提问 | 自动化：端到端 | 回答和引用均不涉及该文档（硬性） |

## 7. 时间处理

有效期记在版本上，每个时间值带来源等级；没有依据的生效时间不推断。三类时间查询共用一条检索链路，只是过滤条件不同。

### 7.1 来源等级

| 时间来源 | 等级 | 能支撑的结论 |
| --- | --- | --- |
| 正文写明，或审核人补录 | `explicit` | 可直接支撑“当前生效”“某天有效”，并引用原句 |
| 只有上传或源系统时间 | `inferred` | 可以作答，但须说明依据；单独支撑的时效结论标为“未验证” |
| 没有任何时间 | `unknown` | 内容可以引用，不参与时间判断 |

只有规范类文档维护生效区间。记录类文档只记 `doc_date`，按时点处理。

### 7.2 抽取规则

规则优先，模型兜底。

| 抽取对象 | 规则示例 |
| --- | --- |
| 生效日 | “自 X 起施行 / 执行 / 生效 / 实施”“X 起实施” |
| 作废日 | “有效期至 X”“X 起废止 / 停止执行” |
| 废止关系 | “《…》同时废止”“原《…》不再执行” |
| 相对表述 | “自发布之日起施行”“自发布之日起 N 日后施行” |
| 文档日期 | 落款日期、报告期 |

- 相对表述在能取得发布日期时换算成具体日期；取不到时，原文写入 `unresolved_text`，等级为 `unknown`，不给出日期。
- 模型兜底使用结构化输出，必须返回原句位置；没有原句位置的抽取结果丢弃。
- 废止关系中的被废止文件按标题匹配已有文档；匹配不到时保留待确认，由审核人处理。

### 7.3 作废日的推导

多数文件只写生效日，作废由后来的文件宣布，所以 `valid_to` 主要由关系推导：

| 情况 | 旧版本的 `valid_to` | 等级 |
| --- | --- | --- |
| 新版本生效日为 `explicit` | 新版本的生效日 | `explicit` |
| 新版本生效日不是 `explicit` | 新版本的审核通过日 | `inferred` |
| 新文件正文点名废止旧文件 | 新文件的生效日（无则审核通过日） | 同新文件生效日的等级 |
| 文件自身写明有效期至 | 写明的日期 | `explicit` |

`valid_to` 表示不再有效的第一天。

### 7.4 三类时间查询

| 查询 | 典型问法 | 索引内过滤 | 检索后处理 |
| --- | --- | --- | --- |
| 当前生效 | 现行规定是什么 | `valid_from` 不晚于今天或为空；`valid_to` 晚于今天或为空 | 优先采用 `explicit` |
| 历史时点 D | 某天生效的是什么 | `valid_from` 不晚于 D 或为空；`valid_to` 晚于 D 或为空 | 同上 |
| 回溯到 T | 截至某天系统知道什么 | `approved_at` 不晚于 T | 取 T 时刻记录的有效期和关系，替换索引中的当前值后再判断 |

```sql
-- 某版本在系统时间 T 时记录的有效期
SELECT valid_from, valid_from_grade, valid_to, valid_to_grade
FROM version_validity
WHERE version_id = :version_id
  AND recorded_at IS NOT NULL
  AND recorded_at <= :t
  AND (replaced_at IS NULL OR replaced_at > :t);

-- T 时刻已知的取代关系
SELECT from_version_id, to_version_id
FROM version_relation
WHERE relation = 'supersedes'
  AND recorded_at IS NOT NULL
  AND recorded_at <= :t
  AND (retracted_at IS NULL OR retracted_at > :t);
```

规则：

- **归档文档不参与。** 归档版本不在索引中，三类查询都查不到；取消归档后按原 `approved_at` 重新参与回溯。同一个回溯问题的答案因此会随归档和取消归档变化，这一口径写入产品说明。
- **空值不过滤。** 有效期为空的规范类文档仍参与检索，排序靠后；由它支撑的时效结论标为“未验证”。
- **记录类按时点。** 历史时点查询只取 `doc_date` 不晚于 D 的；当前查询按 `doc_date` 从新到旧排序。
- **两个时间可同时给定。** 先按 T 回溯，再按 D 过滤。
- **回溯放大候选。** 回溯查询的候选数放大到 3 倍（初值）后再筛选。
- **冲突处理。** `explicit` 优先于 `inferred` 和 `unknown`；两份都不是 `explicit` 且内容矛盾时，两份都列出，系统不代为选择。

### 7.5 时间点的识别与回显

时间点先用规则从问题中解析（“截至”“当时”“X 年 X 月 X 日”“修订前”等），规则无法确定时由模型解析。解析出的时间点写在回答开头，例如“按 2026 年 6 月 2 日生效的版本回答”。接口参数 `as_of_valid` 和 `as_of_system` 优先于解析结果。

### 7.6 验收

| 编号 | 验收内容 | 方式 | 通过标准 |
| --- | --- | --- | --- |
| AC-7-1 | 样例正确性：事实表样例 Q01–Q08 | 自动化：端到端冒烟 | 全部正确（硬性） |
| AC-7-2 | 回溯隔离：回溯到 T 时，T 之后审核通过的版本不出现，T 之后的更正不生效 | 自动化 | 违规数为 0（硬性） |
| AC-7-3 | 来源等级如实：回答标注的等级与事实表一致；仅由 `inferred` 或空值支撑的时效结论标为“未验证” | 自动化：对合成集逐条比对 | 不一致数为 0（硬性） |
| AC-7-4 | 作废日推导：7.3 每种情况的正反用例 | 自动化：单元测试 | 全部通过 |
| AC-7-5 | 相对表述：无法换算时不输出日期 | 自动化：单元测试 | 全部通过（硬性） |
| AC-7-6 | 时间点回显与参数优先 | 自动化 | 有时间点的回答均有回显；参数覆盖解析结果 |
| AC-7-7 | 时间抽取准确率 | 评测：合成集与官方文件样本 | 待基线 |
| AC-7-8 | 历史时点与回溯查询准确率 | 评测：合成集 | 待基线 |

## 8. 查询执行

一次提问在 `orchestrator` 里是一个有预算上限的状态机：Router 用规则选入口，三种模式共用检索、生成和组装节点，证据不足时逐级升级，预算用尽仍无法确认就拒答。

&#91;embedded content: 查询执行状态机 · 3 种模式，2 个回路，2 条升级路径\]

### 8.1 路由规则

| 顺序 | 条件 | 入口 |
| --- | --- | --- |
| 1 | 问题含明确日期、时间点或版本用语（“截至”“当时”“修订前”“旧版”“第 N 版”），或接口传入了时间参数 | Verified |
| 2 | 问题含比较、因果或多跳用语（“区别”“对比”“变化”“为什么”“分别”“哪些……的……”） | Deep |
| 3 | 其他 | Fast |

检索之后再判断一次强制验证：所用证据来自规范类文档，或命中租户追加的规则，即转入 Verified。

接口的 `mode_hint` 只能把模式提高，不能低于 Router 的决定。

### 8.2 升级条件

| 升级 | 信号 |
| --- | --- |
| Fast → Deep | 重排后最高分低于阈值；引用检查失败；问题中有部分要点没有证据覆盖 |
| Fast 或 Deep → Verified | 证据之间存在冲突；命中已被取代或已过期的版本；结论依赖图表数值；命中强制验证清单 |
| 任意模式 → 拒答 | 预算用尽仍有证据缺口；核心结论验证不通过且补检索无果 |

阈值存放在 `tenant_config.thresholds`，按所用模型和语料标定。

### 8.3 三种模式的流程

**Fast：** 检索 → 生成 → 引用检查（第 9 节的确定性检查）→ 判断是否需要验证 → 组装。

**Deep：** 选择计划模板 → 按步骤检索 → 缺口检查 → 有缺口且预算未用尽则再规划 → 生成 → 判断是否需要验证 → 组装。计划模板固定为三种：

| 模板 | 步骤 |
| --- | --- |
| 比较 | 拆出比较对象 → 分别检索 → 对齐要比较的字段 → 生成差异 |
| 多跳 | 识别第一跳 → 检索 → 用结果构造下一跳 → 重复至问题闭合 |
| 因果 | 检索现象 → 检索相关变更记录与说明 → 关联生成 |

**Verified：** 结论拆分 → 确定性检查 → 语义检查 → 不通过的结论定向补检索一轮 → 再验证 → 组装。Verified 优先复用前面模式已取得的证据。

### 8.5 预算与异步

| 模式 | 检索轮数上限（初值） | 同步时限（初值） |
| --- | --- | --- |
| Fast | 1 | 按部署形态和模型设定，目标 P95 小于 4 秒 |
| Deep | 3 | 30 秒；超过后转为后台任务 |
| Verified | 补检索 1 轮 | 30 秒；超过后转为后台任务 |

转为后台任务后，查询接口返回会话编号和 running 状态；客户端通过会话接口查看进度，可以取消；进程重启后任务从检查点恢复。

### 8.6 回答组装

组装规则由代码执行：

| 结论状态 | 处理 |
| --- | --- |
| supported | 作为事实陈述，附引用 |
| unverified | 保留，标注“未验证” |
| unsupported | 删除；如果是问题的核心结论，整个回答改为拒答，并说明缺少什么 |

每个回答附带：所用模式、每条引用的文档版本和定位、时间来源等级说明、时间点回显（如有）。拒答时不透露任何用户无权查看的文档的存在。

## 9. 验证层

代码做确定性检查，模型只判断证据是否真正支持结论；拿不准的一律标为“未验证”。验证器的错误率用独立评测集单独度量，不参与给自己打分。

### 9.1 结论拆分

模型把回答拆成原子结论，每条结论列出所依据的证据 id，使用结构化输出。引用了不存在于本次检索结果中的证据 id 的结论，直接判为 unsupported。

### 9.2 确定性检查

| 检查 | 做法 | 不通过时 |
| --- | --- | --- |
| `locator_exists` | 所引证据存在，定位指向的页码、表格单元格或图表区域在原文中存在 | unsupported |
| `value_match` | 从结论中抽取数值、日期、单位，规范化后（全角半角、万与千、日期写法、千分位）必须出现在所引证据的内容中 | unsupported |
| `time_valid` | 所引版本在目标时间有效：当前查询看今天，历史时点看 D，回溯看 T 时刻记录的有效期 | 版本确定无效时为 unsupported；仅由 `inferred` 或空值支撑时为 unverified |
| `authorized` | 调用授权接口的 `check` 再核对一次 | 移除该证据，结论按剩余证据重新检查，并记录安全告警 |

### 9.3 语义检查

通过确定性检查的结论交给模型判断：给定结论和所引证据原文，输出 supported、unsupported 或 unverified，以及置信度。置信度低于阈值的一律视为 unverified。阈值按所用模型标定，标定目标是把误通过率压到门槛以下，宁可多标“未验证”。

### 9.4 修复

对 unsupported 的结论，以结论内容为查询定向补检索一轮，取得新证据后重新执行 9.2 和 9.3。仍不通过的结论删除；它若是核心结论，整个回答改为拒答。

### 9.5 验收

| 编号 | 验收内容 | 方式 | 通过标准 |
| --- | --- | --- | --- |
| AC-9-1 | 四项确定性检查各有不少于 20 个正例和 20 个反例 | 自动化：单元测试 | 全部通过（硬性） |
| AC-9-2 | 扰动用例：事实表样例 Q16，把 650 改成 680 | 自动化：冒烟 | 判为不支持（硬性） |
| AC-9-3 | 误通过率与误拒率 | 评测：LLM-AggreFact 原样评测，加合成扰动集（改数值、改日期、换版本、换主体） | 待基线；误通过率优先 |
| AC-9-4 | Claim 证据支持率 | 评测：人工核对的结论集 | 不低于 95% |
| AC-9-5 | 评测独立：标定阈值用的数据与评测用的数据分开 | 人工检查：评审数据集划分记录 | 无交叉 |

## 10. 权限与安全

权限全部由代码执行，模型没有任何决定权：授权范围下推到索引过滤，证据返回前在数据库里再核对一次，授权服务不可用时默认拒绝。

### 10.1 校验链路

1. `query-api` 校验身份令牌。参考实现用本地账号加角色；客户现场通过授权接口接入 SSO。
2. 调用授权接口 `resolve`，把用户解析为授权范围：租户、角色和用户组列表、过期时间。授权接口不可用时直接拒绝请求。
3. `orchestrator` 只持有授权范围的句柄，范围内容不写入状态对象，不进入模型上下文。
4. `retrieval` 把授权范围编译成 `tenant_id` 与 `principals` 过滤条件，下推到索引；缺少授权范围的请求在入口被拒绝。
5. 取回候选后调用授权接口 `check`，在数据库中核对每条证据当前的权限和版本状态，剔除不通过的。
6. 取代、冲突等关系，只有两端版本都通过校验时才返回。
7. 缓存键包含租户、授权范围哈希和索引构建编号；权限变更、归档、取消归档事件主动清除相关缓存。
8. `query_log` 记录授权决定。

### 10.2 泄露面

| 泄露面 | 风险 | 处理 |
| --- | --- | --- |
| 权限同步延迟 | 源系统已撤权，索引仍可检索到 | 连接器声明撤权生效的最长延迟；先更新数据库再更新索引；延迟窗口内由第 5 步拦截 |
| 派生关系 | 冲突、取代提示暴露无权文档的存在 | 关系两端都通过授权才返回；拒答文本不提及无权文档 |
| 证据接口 | 通过枚举证据 id 探测文档存在 | 无权访问时返回 404，与不存在无法区分 |
| 可观测链路 | Trace 和评测记录保存了原文片段 | 按同一套权限访问；按 `trace_retention_days` 定期清理，默认 30 天 |
| 缓存 | 跨用户或跨权限范围命中 | 见 10.1 第 7 步 |

### 10.3 提示注入防护

- 检索到的内容一律作为数据放在明确的分隔区内，系统提示声明其中的任何指令都不执行。
- 模型没有可调用的工具能改变授权范围或读取范围以外的数据；Deep 模式的动作限定在检索、取原文、取版本三类。
- 因为权限由代码执行，注入最多影响回答内容，不能造成越权。

### 10.4 数据保护与审计

- 传输全程使用 TLS；静态加密由部署环境的磁盘或数据库加密提供。
- 精简版调用线上模型时，文档内容会发送到模型接口；部署说明中向客户明示。
- 审计数据包括：每次查询的 `query_log`、全部 `lifecycle_event`、审核决定及审核人。

### 10.5 验收

| 编号 | 验收内容 | 方式 | 通过标准 |
| --- | --- | --- | --- |
| AC-10-1 | 越权检索与引用：每个角色对每个查询各执行一次 | 安全测试：自动化 | 越权数为 0（硬性） |
| AC-10-2 | 关系泄露：事实表样例 Q09 类用例，检查回答、冲突提示、拒答文本 | 安全测试：自动化 | 无权文档的存在未被透露（硬性） |
| AC-10-3 | 撤权：撤权后立即提问，以及在声明的延迟之后提问 | 安全测试：自动化 | 两种情况都检索不到（硬性） |
| AC-10-4 | 缓存隔离：权限不同的两个用户连续问同一问题 | 安全测试：自动化 | 无串用（硬性） |
| AC-10-5 | 授权服务不可用 | 故障注入 | 请求被拒绝（硬性） |
| AC-10-6 | 证据接口：无权与不存在的 id 返回相同结果 | 自动化 | 均为 404（硬性） |

| AC-10-9 | 审计完整：`query_log` 必填字段完整率 | 自动化 | 100%（硬性） |
| AC-10-10 | Trace 清理：超过保留天数的记录被删除 | 自动化 | 通过 |

## 11. 接口规范

对外是 11 个 HTTP 操作，对接层是 3 个按客户实现的接口；完整定义以 OpenAPI 文件（仓库中的 eaer/api/openapi.yaml，接口进程的 /openapi.json 展示的就是它）为准，该文件与代码一同维护。

### 11.1 通用约定

- 路径前缀 `/v1`，请求与响应为 JSON，身份令牌放在 `Authorization: Bearer` 头中。
- 每个响应带 `request_id`；错误响应格式为 `{"code", "message", "request_id"}`。
- 列表接口用游标分页：`cursor` 与 `limit`，返回 `next_cursor`。

| HTTP 状态 | code | 场景 |
| --- | --- | --- |
| 400 | `invalid_request` | 参数缺失或格式错误 |
| 401 | `unauthenticated` | 令牌无效或过期 |
| 403 | `forbidden` | 无权执行该操作（如非审核人提交审核） |
| 404 | `not_found` | 资源不存在，或无权查看（两者不区分） |
| 409 | `invalid_state` | 状态不允许，如删除可搜索版本 |
| 429 | `rate_limited` | 超过频率限制 |
| 503 | `authz_unavailable` | 授权服务不可用 |

### 11.2 对外接口

| 操作 | 用途 |
| --- | --- |
| `POST /v1/query` | 提问 |
| `GET /v1/sessions/{id}` | 会话历史、引用记录、异步任务进度 |
| `POST /v1/sessions/{id}/cancel` | 取消进行中的异步查询 |
| `GET /v1/evidence/{id}` | 取证据原文与定位；已归档返回归档提示 |
| `POST /v1/documents` | 上传文档，进入待审核 |
| `GET /v1/review/tasks` | 列出审核任务，可按批次和状态筛选 |
| `POST /v1/review/decisions` | 提交审核决定，支持一次多份 |
| `POST /v1/documents/{id}/archive` | 归档文档 |

## 12. 模型接入

生成、Embedding、重排三类模型都经统一的 `ModelClient` 调用；首期只针对线上模型调优和评测，客户自部署模型经同一接口接入，补测通过准入检查后才开启相应模式。

### 12.1 能力声明

每种模式声明所需能力，接口层按 `capabilities()` 的结果决定开启哪些功能：

| 模式 | 所需能力 | 能力不足时 |
| --- | --- | --- |
| Fast | 生成、Embedding、重排 | 无法运行，部署时报错 |
| Deep | 稳定的结构化输出，足够的上下文长度 | 关闭 Deep，问题由 Fast 回答并说明 |
| Verified | 稳定的结构化输出，足够的上下文长度 | 关闭 Verified；时效性和强制验证类问题以“未验证”标注作答 |
| 图表解析（入库） | 视觉 | 跳过图表深度解析，只保留文本 |

上下文长度的最低要求在第 9–12 周根据 Deep 和 Verified 的实际输入量确定。

### 12.2 线上模型

- 精简版默认配置线上模型；生成、Embedding、重排可分别配置不同的服务。
- 每次调用记录 token 数、调用次数和耗时，汇总到 `query_log.cost`；入库阶段的调用单独计量。
- 超时与重试：单次调用超时 30 秒（初值），可重试错误重试 2 次，带退避；最终失败时返回明确错误，不返回空答案。
- 文档内容会发送到线上模型接口，部署说明中向客户明示。

### 12.3 自部署模型与准入

1. 客户在自己的环境中用 `eval` 模块跑同一套评测集，数据不出域。
2. `eval` 用标定集重新标定路由、语义检查等阈值，写入 `tenant_config.thresholds`。
3. 准入检查：验证器误通过率达标才开启 Verified；Deep 的答案正确率达标才开启 Deep。未达标的模式保持关闭。
4. 结果生成该客户的能力矩阵：各模式是否可用、准确率、误通过率、响应时间、硬件要求。

自助评测工具是产品标配；由我们代为补测和调参作为收费服务。

## 14. 评测体系

通用能力用许可允许的开源数据集评测；中文评测和差异化能力（版本、生效时间、回溯、归档、权限）用合成数据评测。合成的做法是先填事实表，再生成文档和问题，标准答案由程序计算。

### 14.1 数据集

| 数据集 | 用途 | 使用范围 |
| --- | --- | --- |
| FRAMES | 多跳问答、三方对比 | 可对外展示（Apache 2.0） |
| MultiHop-RAG | 多文档问答、无答案查询 | 可对外展示，需署名（ODC-BY） |
| ViDoRe V3 | 图表与表格检索（英文、法文语料） | 可对外展示，需署名（CC BY 4.0，各子集逐个确认） |
| LLM-AggreFact | 验证器的误通过率与误拒率 | 原样用于评测并报告分数，不改编、不训练（CC BY-ND 4.0） |
| HoH、VersionQA、CHaystack | 过期信息、版本、中文文档检索 | 仅内部开发使用，结果不对外 |
| 自建合成集 | 中文评测；版本、时间、回溯、冲突、归档、权限、验证器扰动 | 可对外展示，注明为合成数据 |

RGB、DragonBall、CRUD-RAG 只借鉴任务设计和数据结构，内容全部自行合成，不复制、改写或翻译其题目与文档，不把其数据交给模型仿写，不直接使用 RAGEval 的代码和提示词。对外材料写“参照某数据集的任务设计自建”并引用原论文。

### 14.2 合成流程

1. **填写事实表。** 使用[合成评测集事实表模板](https://claude.ai/artifact/JoWTm385CLfbhRDovzNhTP)：角色、文档、版本、事实、事件、查询六张表。种子优先使用法律、法规和国家机关的正式文件，其次是自编内容。
2. **校验。** 生成程序检查事实表的约束：编号唯一、外键存在、取代关系无环、应拒答的查询不填依据事实。
3. **生成文档。** 按版本表的“生效日写法”用模板生成文档（需要更接近真实的文风时，再用非被评测的模型改写措辞，改写结果重新经第 4 步检查）：正文写明、只有上传时间、没有时间三种。表格类事实生成表格，图表类事实生成图表。
4. **检查文档。** 程序确认每份文档包含事实表中该版本的全部数值和日期。
5. **计算答案。** 程序按时间回放事件到每个查询的提问日，计算预期答案、预期来源等级和是否应拒答，回填查询表。
6. **人工抽检。** 抽检不少于 5% 的问答对后，冻结为一个评测集版本。

第 2–5 步已由 `factset` 工具实现：在事实表样例上，16 个查询的计算结果与人工答案全部一致；10 类错误数据均被拒绝；生成的 Word 与 HTML 文档全部通过检查，6 类篡改均被发现。尚未完成的是模型改写和第 6 步人工抽检。

评测需要按历史日期装载文档、执行审核和事件，回溯类查询才有意义。`render` 输出的 `manifest.json` 按审核通过日列出全部版本和事件；`eval` 模块通过一个只在评测环境启用的装载入口写入这些历史日期，生产接口仍以当前时间记录，不受影响。检索评测运行器同样逐日回放，每个查询在它的提问日提出。

### 14.3 集合划分与样本量

- 每个评测集版本分为标定集（30%）和测试集（70%）：阈值只在标定集上调，指标只在测试集上报。
- 高风险类别（历史时点、回溯、冲突、归档、权限边界）各不少于 300 条；其他类别各不少于 100 条（初值）。
